# Smart Pursuit Agency OS

A small, opinionated system for one job: find local businesses with weak
websites, prove it with a **measured** 10-page audit, and write honest outreach
drafts that a human sends.

It was built around a real audit that a client has already received, so the output
is not "a document generated by a script". It is the same document, produced from
fresh measurements.

> **This is the public export.** The reference audit itself — a named business's
> measurements, screenshots and delivered PDF — is withheld, because it belongs
> to that client and is marked private and confidential. Everything needed to
> produce an equivalent audit is here; see `examples/README.md`.

> **Nothing is sent automatically.** There is no SMTP client, no scheduler and no
> token in this repo. The system writes Markdown drafts; the operator sends them.

---

## What it does

```
leads → dedupe → measure → score → findings → 10-page HTML → PDF
                                                       → QA → third-eye verify
                                                       → email drafts (1 + 3)
```

| Command | What it produces |
| --- | --- |
| `run --state "Andhra Pradesh"` | the daily driver: fetch leads, audit only the ones never audited, write their drafts |
| `leads --state gujarat` | new business leads, duplicate-checked, from OSM / Places / CSV |
| `audit --url …` | a measured 10-page A4 audit PDF + `audit.json` + `qa.json` + `verify.json` |
| `sequence --audit …` | four email drafts dated day 0, +3, +6, +9 |
| `verify --audit …` | re-runs the third-eye gate on an existing audit |
| `status` | what is in the lead and audit registries |
| `selftest` | proves the scoring rubric still reproduces the reference |

## What it does not do

- It does **not** build demo websites. Audit first; a demo is a separate decision.
- It does **not** send email.
- It does **not** guess contact details, testimonials, prices or statistics.
- It does **not** scrape directories whose terms forbid it.

## Quick start

Requires **Node 20+** and an installed **Google Chrome**.

```bash
npm install
npm run selftest          # must print 3/4/2/6/5 -> 36
```

The rubric is calibrated against a delivered audit. `npm run selftest` recomputes
those calibration scores from the rubric in `src/findings.mjs` and must print
`speed 3 · mobile 4 · conversion 2 · design 6 · seo 5 → 36`. If it does not, the
rubric has drifted and no audit should be produced until it is fixed.

The delivered reference document itself is not public. `examples/README.md`
explains what it contained and how to recreate one for a new lead.

Audit a real site:

```bash
npm run leads -- --state gujarat --niches dentist --limit 15
npm run audit -- --url https://the-lead.example --name "The Lead" --city Ahmedabad --state gujarat
npm run sequence -- --audit reports/<slug>/audit.json --send-date 2026-11-10
```

Or let the daily driver do all of it for a whole state:

```bash
npm run run -- --state "Andhra Pradesh"           # fetch, audit what is new, draft
npm run run -- --state "Andhra Pradesh" --dry-run # show the queue, measure nothing
npm run daily -- --state "Kerala" --max 3         # same command, second name
```

The PDF is named after the business:
`reports/<slug>/Smart-Pursuit-Audit-<Business-Name>.pdf`. A second run on the same
day finds nothing to do, because the queue is computed from the lead and audit
registries rather than from a "last run" timestamp.

On PowerShell, use `npm.cmd` instead of `npm`.

## The three guarantees

### 1. No number without a source

The report is rendered from `audit.json`, which is built from a raw measurement
file. `verify.mjs` re-reads the raw file, recomputes every score and fact, and
scans the visible text for numbers that are not traceable. A single untraceable
number blocks the PDF.

### 2. No duplicate audit

`data/audits.json` is an append-only registry keyed on the normalised domain. The
audit command checks it **before touching the network**. A domain inside the
60-day cooldown is refused. `--force` exists for deliberate before/after proof,
not for convenience.

### 3. No silent design drift

`src/styles.css` and `src/fonts.css` were extracted verbatim from the reference
audit. The renderer emits the same ten pages, the same furniture, the same type
scale. `qa.mjs` measures the layout in Chromium at A4; `verify.mjs` checks the PDF
is 10 pages and A4.

## Binaries and the `.b64` convention

The pipeline produces binaries: the PDF, and the screenshots it embeds. Some
transport paths (file APIs, chat tools, patch-based agents) only carry text, so
`tools/encode-b64.mjs` writes a `.b64` beside a `.sha256`, and
`tools/decode-b64.mjs` restores it, verifying the hash first and refusing to
write a corrupt file:

```bash
node tools/encode-b64.mjs path/to/file.pdf
node tools/decode-b64.mjs                 # restores every sidecar it finds
node tools/decode-b64.mjs --verify-only   # checks hashes, writes nothing
```

No binary in this public export is a client document. Real audit output is
written to `reports/`, which is git-ignored, because a client's audit is theirs.

## What the quality bar was, and why it is not here

The renderer was built to reproduce a delivered audit exactly: ten A4 pages,
six findings, a specific gauge, the same page furniture and type scale. That
document belonged to a named business, so it is not in this repository — not the
PDF, not its screenshots, not its measurement file.

What survives in the repo is everything that defines the bar:

| Guard | What it proves |
| --- | --- |
| `npm run selftest` | the rubric still scores the calibration case `3 / 4 / 2 / 6 / 5 → 36` |
| `src/styles.css` | the exact design system, extracted verbatim from the delivered document |
| `docs/DESIGN-SPEC.md` | page-by-page furniture, type scale, palette, and the slop list |
| `docs/AUDIT-SPEC.md` | the 10-page contract, the rubric, and what the third eye checks |
| `node tools/class-diff.mjs` | every emitted class has a rule; 10 pages, 6 findings, ≤4 images, 9 footers |

If you need the original for a side-by-side, ask the agency — do not reconstruct
it from memory, and do not invent one.

## Known limits — read before you sell this as general-purpose

The pipeline is general. The **findings copy is not**. `src/findings.mjs` writes
for one kind of business: a local, appointment-driven practice whose revenue comes
from enquiries (dentist, clinic, physio, salon, law firm). Its sentences say
"patient" and "booking" on purpose, because vague copy reads as filler and filler
does not sell.

If you audit a different kind of business:

- set `agency.auditLabel` in `config/settings.json` to the right noun;
- edit the finding copy in `src/findings.mjs` — every `why` / `fix` string is
  plain text, no measurement lives there;
- keep the rubric arithmetic untouched, or `npm run selftest` will fail and that
  is the point;
- re-read the tone rule in `AGENTS.md` before you touch a sentence.

Do not paper over this by generating copy with a language model at render time.
The report's credibility rests on every sentence being checkable against a
measurement.

Other honest limits:

- **Competitor benchmarks need a target list.** Without one, page 7 falls back to
  Google's published targets, labelled as targets.
- **Lighthouse is local.** Numbers will differ from PageSpeed Insights by a few
  points. Quote the measurement you actually took, never the API you did not call.
- **Screenshots are the client's site.** They are evidence, not decoration, and
  they are never committed to this repo.
- **The 60-day cooldown is a promise.** A business that received an audit should
  not receive the same one twice. The daily runner enforces it without a flag:
  `pendingLeads()` builds the queue from `data/leads.json` and
  `data/audits.json`, so an audited domain is never queued again.
